# 코드 구조 설명

이 문서는 "어떤 파일이 무슨 일을 하고, 질문 하나가 어떤 길을 거쳐 답이 되는지"를 설명합니다.
실행 명령은 [README](../README.md)에 있습니다. 챗봇 코드는 **코퍼스 `data/corpus.jsonl`(기사 132건, 803청크)**를 읽고, 평가는 **개발셋 v3·검증셋 v1·홀드아웃 v2**로 합니다([데이터](데이터.md)). 화면(`app.py`, `ui/`)의 설계는 [서비스설계](서비스설계.md)에 있습니다.

## 1. 한눈에 보는 흐름

큰 틀만 적었습니다. 단계마다 어떤 파일을 읽고 무엇을 만드는지는 2-4장에 있습니다.

```
[준비 단계]  데이터가 바뀔 때만 (2장)
 (0) 기사 고르기
   │
   ▼
 (1) 실록 원문 ZIP에서 기사 뽑기
   │
   ▼
 (2) 정제·청킹
   │
   ▼
 (3) 번역 → 코퍼스 만들기
   │
   ▼
 (4) 벡터 DB 만들기

[질문 단계]  질문할 때마다 (3장)
 (1) 누가 답할지와 시점 정하기 (조건 C·D1·D2)
   │
   ▼
 (2) 검색: 임베딩 + BM25 → 합치기 → 리랭커가 6개 고르며 질문 속 전제도 판정
   │
   ▼
 (3) 프롬프트 만들기
   │
   ▼
 (4) 답변

[평가 단계]  실험할 때 (4장)
 (1) 평가셋 문항마다 질문 단계 돌리기
   │
   ▼
 (2) 자동 점검 · 자동 채점 · 가채점
   │
   ▼
 (3) 원인 분석 (오답노트)
```

## 2. 준비 단계

데이터가 바뀔 때만 돌립니다. 명령은 README "데이터 다시 만들기"에 있습니다.

```
 (0) 기사 고르기
     한능검 기출 집계(docs/기록/데이터구축/) → 사람·AI가 기사 132건을 골라 목록에 적음
     docs/기록/데이터구축/고른기사목록.csv  ── 기사 ID 132개와 주제·고른 이유. 어떤 기사를 쓸지 정하는 유일한 곳(새 기사는 끝에 더함)
     ZIP에서 뽑을 때 한 번만 쓰는 목록이라 사람용 기록 폴더에 둠
   │
   ▼
 (1) 실록 원문 ZIP에서 기사 뽑기   scripts/extract_articles.py
     입력: 공공데이터 실록 ZIP(한문, 137MB, 기사 38만여 건, 사용자 컴퓨터에만) + 고른기사목록.csv
     출력: data/raw_xml/            기사 원본 XML 조각 (청킹이 읽음)
           data/articles.jsonl      같은 원문을 날짜·제목·문단으로 풀어 둔 것 (코퍼스 만들기·테스트가 읽음)
   │
   ▼
 (2) 정제·청킹   scripts/chunk_articles.py  (ZIP·목록 필요 없음)
     articles.jsonl의 기사 순서대로 raw_xml/을 정제·청킹 규칙서대로 자름
     출력: data/청크초안_20260930_v2.jsonl  ── 청크 803개 (규칙서 v2, 원문 + 화자·시점 초안 + 머리말)
           docs/기록/데이터가공/  ── 통계·정제 횟수·수동 검사표 (사람용)
   │
   ▼
 (3) 번역 → 코퍼스 만들기   scripts/build_corpus.py
     build_corpus.py --dump 로 기사 하나의 청크 한문을 띄우고 → AI가 청크마다 번역·화자·알게 된 때를
     data/번역/*.jsonl 에 적음(사람이 검수하며 고치는 원본) → build_corpus.py 로 청크초안 + 번역을 합침
     출력: data/corpus.jsonl  ── 132건 803청크 (원문 / 번역 / 화자 / 알려진 시점 / 쉬운 말 풀이), 챗봇이 읽는 코퍼스
     쉬운 말 풀이(gloss)는 scripts/gloss_add.py·gloss_fix.py로 data/번역/ 에 넣은 뒤 build_corpus.py 로 옮김
   │
   ▼
 (4) 벡터 DB 만들기   python -m sillok_rag.cli build-db
     청크마다 제목·화자·번역문을 OpenAI 임베딩으로 벡터로 바꿔 저장(유료)
     코퍼스 지문(청크 ID·검색 본문·시점 키)을 함께 저장해, 번역·화자·시점을 고친 뒤 DB를 다시 안 만들면 실행 전에 알려 줌
     새 DB는 임시 컬렉션에 끝까지 만든 뒤 기존 것과 바꿈 → 임베딩·저장이 실패해도 기존 DB가 남음(2026-10-07, 전체검토 2-8 1번)
     출력: chroma_db/  ── 로컬 벡터 DB (검색용, git 제외)
```

- **청킹이 `articles.jsonl`이 아니라 `raw_xml`을 읽는 이유**: `articles.jsonl`은 XML에서 글자만 이어 붙인 것이라 인명·지명 표시, 사론(사관의 평가), 주석 종류(원래 주·교감주·번역주)가 사라집니다. 청킹은 이 표시로 화자를 찾고, 사론을 "후일 기록"으로 떼고, 번역주를 빼므로 표시가 살아 있는 원본이 필요합니다.
- **번역을 청크 단위로 하는 이유**: 검색·시점 필터는 청크마다 번역과 화자·알게 되는 때가 따로 있어야 합니다. 기사 전체를 번역한 뒤 자르면 한문과 번역의 경계를 맞추기 어렵고, 정제에서 뺀 번역주·사론까지 번역하게 됩니다. `build_corpus.py --dump`가 기사 하나의 청크를 순서대로 모두 보여 줘서, 번역할 때 기사 전체 문맥은 그대로 봅니다.

## 3. 질문 단계

질문이 들어올 때마다 이 순서로 돕니다. 코드는 `sillok_rag/chat.py`(흐름), `retrieval.py`(검색), `prompts.py`(프롬프트), `llm.py`(모델 호출)입니다.

```
 (1) 누가 답할지와 시점 정하기   chat.py
     사실 질문이면 "학습 도우미", 인물 인터뷰면 "인물"이 답함
     D2에서 "역할 벗고 알려줘" 같은 말이면 "해설자"가 따로 답하고, 그 문답은 인물의 대화 기록에서 뺌
     D1·D2에서 인물이 답할 때는 장면 시점(예: 1444-02-20)을 검색에 넘겨 그 뒤에 알게 된 청크를 뺌 (조건은 6장)
   │
   ▼
 (2) 검색   retrieval.py  ── 청크 803개 중 6개 + 전제 판정 메모 (아래 자세히)
   │
   ▼
 (3) 프롬프트 만들기   prompts.py
     답하는 쪽의 규칙 문장(사실 질문 / 인물 / 해설자) + [자료](고른 6개의 번역문과 출처·기록일·화자)
     리랭커가 질문 속 틀린 전제를 찾았으면 "답하기 전 점검" 메모(근거 문장 포함)도 함께
     인물이면 "이 인물이 이 시점에 아는 사실" 카드와 앞선 대화도 함께
   │
   ▼
 (4) 답변   llm.py
     gpt-6-luna(생각 수준 medium, 2026-10-07부터)가 답함 → 화면(app.py) 또는 결과 파일(results/)

 (+) 근거 대조   evidence.py  (화면에서 실제 답변을 켜면 답마다 호출 한 번 더. 근거 기사 창과 취재 목표 체크에 씀)
     답변 문장마다 실록 기록 / 실록 풀이 / 인물 시점 / AI 창작 표시, 실록 기록 문장에는 근거 기사 카드
```

### 검색은 이렇게 돼요 (하이브리드 + 리랭커)

질문 하나가 들어오면 청크 803개 중 6개를 골라 답변 모델에게 줍니다(2026-10-07 4 → 6, `config.TOP_K`). 코드는 `sillok_rag/retrieval.py`, 조립은 `cli.make_retriever()`입니다.

```
 사용자 질문  (예: "세조가 불경을 펴내려고 새로 만든 관청 이름이 뭐야?")
   │  D1·D2에서 인물이 답할 때는 먼저 시점 필터: 장면 뒤에 알게 된 청크와 '후일 기록'(사론 등)은 처음부터 뺌
   │
   ├─① 임베딩 검색 (ChromaRetriever)
   │     질문을 OpenAI text-embedding-3-large로 숫자 벡터로 바꿈(질문마다 유료, 아주 쌈)
   │     → chroma_db/에 미리 저장한 청크 벡터와 코사인 유사도 비교 → 뜻이 가까운 순서로 1위부터 끝까지
   │     낱말이 달라도 뜻이 비슷하면 찾음. 유사도가 소수점까지 달라 동점이 사실상 없음
   │
   ├─② BM25 검색 (BM25Retriever, 무료)
   │     질문과 청크(기록일·재위년 + 제목·화자·번역문 + 한문 원문)를 두 글자씩 잘라("세조"·"조가"·…) 겹치는 조각에 점수
   │     (쉬운 말 풀이는 여기 넣지 않음. 아래 ②-1로 따로)
   │     여러 청크에 흔한 조각은 낮게, 드문 조각은 높게 → 점수순으로 1위부터 끝까지
   │     같은 낱말이 나와야 찾음. 겹치는 조각이 없으면 0점
   │
   ├─②-1 풀이 BM25 (C안, 2026-10-07, 작업기록 [302])
   │     청크 글 + 쉬운 말 풀이(가중치 0.5)로 BM25를 한 번 더 돌려 상위 5개(0점 제외)를 ③의 후보에만 보탬
   │     "불교 책"처럼 쉬운 말 질문이 풀이 낱말로 잡힘. 합친 순위(RRF)에는 넣지 않음 (config.GLOSS_KEEP)
   ▼
 ③ 합치기 (HybridRetriever, RRF: Reciprocal Rank Fusion)
     청크마다  1/(60 + 임베딩 순위) + 1/(60 + BM25 순위)  → 큰 순서로 20개
     두 검색기의 점수 단위가 달라 점수 대신 순위만 씀. 60은 흔히 쓰는 기본값
     동점(특히 BM25 0점 수백 개)은 모두 공동 순위(평균)를 받음 → 코퍼스 파일 순서가 결과에 끼어들지 않음
     + 임베딩 상위 10개와 BM25 상위 10개(0점 제외), 풀이 BM25 상위 5개를 꼭 더함 → 후보 평균 약 27개(최대 30여 개)
       한쪽 검색기만 위로 찾은 정답이 다른 쪽 순위에 끌려 밀리지 않게 (config.HYBRID_KEEP_EACH)
   ▼
 ④ 리랭커 (RerankRetriever)
     gpt-6-luna(생각 수준 low)가 질문과 후보들의 제목·화자·날짜·번역문을 읽고 6개를 골라 순서를 정함(풀이는 주지 않음)
     같은 호출에서 질문 속 전제(누가·언제·무엇·몇)를 하나씩 나눠 맞음/틀림/확인 불가로 판정하고 근거 문장을 글자 그대로 옮김
     → '틀림'이고 근거 문장이 고른 청크에 있을 때만 답변 모델에 "답하기 전 점검" 메모로 넘김 (config.RERANK_CHECK, 작업기록 [304]·[313])
     모델 답을 못 쓰면 ③의 순서대로 6개. 적게 고르면 ③의 순서로 채움
   ▼
 ⑤ 고른 6개(+ 전제 판정 메모)를 [자료]로 붙여 답변 모델(gpt-6-luna, medium)이 답함 (prompts.py)
```

| 단계 | 잘하는 것 | 못하는 것 |
|---|---|---|
| ① 임베딩 | "불교 책 찍는 기관"처럼 낱말이 달라도 뜻으로 찾음 | 고유명사·숫자·날짜가 정확히 맞는지는 약함 |
| ② BM25 | "간경도감", "징비록"처럼 같은 낱말이 있으면 확실히 찾음 | 낱말이 하나도 안 겹치면 못 찾음 |
| ③ 합치기 | 두 검색기가 모두 위에 올린 청크를 확실히 올림. 한쪽 상위 10개는 꼭 후보에 넣음 | 한쪽에서 11위 아래인 청크는 여전히 다른 쪽 순위에 끌려 내려감 |
| ②-1 풀이 BM25 | 질문이 쉬운 말이고 실록이 어려운 용어일 때(HF04 "불경"↔"간경도감") | 흔한 풀이 말('벼슬'·'책')에는 약해서 후보에만 보탬 |
| ④ 리랭커 | 질문 뜻을 읽고 정말 답이 되는 청크를 고름. 틀린 전제를 찾아 메모로 알려 줌 | 후보 밖은 못 봄. 메모가 틀리면 답이 따라감(HF05 v1b) |

**결과 파일에 남는 것**: `retrieved`·`context_ids`는 최종 6개, `check`는 답변에 넘긴 전제 판정 메모, `rerank_trace`는 리랭커에 넘긴 후보와 모델이 고른 것([135]부터). 정답이 어느 단계에서 빠졌는지는 `scripts/retrieval_stage_diag.py`로 봅니다.

**역할 대화의 검색**(2026-10-01, 작업기록 [183]): 인물이 답하는 턴은 시나리오 설정 문장(장면)을 ① 임베딩 검색어 앞과 ④ 리랭커 입력에 함께 줍니다. "오늘 올린 상소"가 다른 상소 기사를 찾던 문제(B1·C1·B9) 때문입니다. ② BM25에는 붙이지 않습니다(장면 낱말이 모든 턴을 같은 기사로 끌어옴). 앞선 대화는 검색에 넣지 않습니다(사관의 틀린 전제가 검색어가 됨).

**지금 알려진 약점**: 질문 말과 실록 말이 다른 경우(HF04 "불경"↔"간경도감", HF05 "손녀"↔"아들의 딸"). 원인과 개선 후보는 [한계와 다음 과제](한계와_다음과제.md)에 있습니다. HF04는 청크의 쉬운 말 풀이를 BM25에 넣으면 120위 → 2위로 올라와([286]), 2026-10-07부터 풀이 BM25 상위 5개를 후보에 보탭니다(C안, [302]). 2026-10-01에 고친 것(한쪽 검색기 상위 10개 보존, BM25 동점 공동 순위, BM25 날짜 색인 [183])은 위 ②·③에 반영돼 있습니다.

## 4. 평가 단계

실험할 때 돌립니다. 순서와 명령은 8장과 README "비교 실험"에 있습니다.

```
 (1) 평가셋 문항마다 질문 단계 돌리기   evaluate.py
     입력: data/eval/ (개발셋 v3 단발 67문항 + 다회차 A·B·C, 검증셋 v1 두 벌, 두 번째 사건 다회차 D·E, 홀드아웃 v2 20문항)
     출력: results/<날짜>_<실험 이름>/<시각>_<평가셋>_<조건>_….jsonl  (실험 이름은 --run)
           문항마다 답 · 최종 청크 6개 · 전제 판정 메모(check) · 리랭커 후보(rerank_trace) · 검색에 장면을 줬는지(search_scene) · 코퍼스 지문
   │
   ▼
 (2) 자동 점검 · 자동 채점 · 가채점
     자동 점검(evaluate.py): 정답 청크가 검색됐나, 핵심어가 빠지지 않았나, 미래 단어가 새지 않았나, 원문에 없는 한문을 인용하지 않았나 (힌트일 뿐)
```

## 5. 청크 하나는 이렇게 생겼어요

`data/corpus.jsonl`의 한 줄 = 청크 하나입니다. (예: 2월 20일 기사 안의 다음 날 석방 부분) 모든 칸의 뜻은 [데이터](데이터.md) 2절 "청크 한 줄의 칸"에 있습니다.

| 칸 | 값 | 의미 |
|---|---|---|
| chunk_id | wda_12602020_001-15 | `기사ID-순번` |
| article_id | wda_12602020_001 | 실록 기사 ID (세종 26년 2월 20일 첫 기사) |
| paragraphs | [8, 9] | 원문 몇 번째 문단인지(0부터 셈, 화면·출처 표기에서는 1을 더해 9·10문단) |
| record_date | 1444-02-20 | 기사에 적힌 날짜 |
| event_date / known_from | 1444-02-21 / 1444-02-21 | 일이 실제로 일어난 때 / **인물이 그 일을 알게 된 때** |
| speaker, speaker_kind, quoted | 사관(서술) / 서술 | 화자, 말의 종류(서술·문답·인용 등), 인용된 사람 |
| original | 翌日, 命釋之, 唯罷昌孫職。… | 한문 원문(정제 규칙 적용) |
| translation | 이튿날 (임금이) 명하여 (의금부에 갇힌 최만리 등 7명을) 석방하게 하되… | 우리가 만든 번역(AI 초안) |
| header, note | [1444년 2월 20일 · 세종 26년 · …] | 맥락 머리말(지금은 채점기 입력에만 쓰고 검색에는 안 들어감. 날짜·재위년은 BM25가 따로 색인), 사람용 메모 |
| gloss | [{"용어": "파직", "풀이": "벼슬에서 물러나게 함"}, …] | 쉬운 말 풀이(풀이가 있는 청크만, 722개). 모델에게는 보내지 않음, 화면 주석·검색용 |

`record_date`와 `known_from`을 따로 두는 게 핵심이에요. 2월 20일 기사 안에 다음 날 석방 이야기가 같이 들어 있어서,
기사 날짜만 보면 "2월 20일의 최만리"가 석방 사실을 알아 버리거든요.

시점 필터(D1·D2)는 `known_from`을 숫자 키로 바꿔 거릅니다(`corpus.known_key`). 예: 1444-02-20 → 14440220.1.
같은 날 안의 순서가 필요할 때만 "이전"·"오후"를 붙입니다(상소는 1444-02-20, 같은 날 세종의 논박·하옥은 "1444-02-20 오후").
사론·졸기처럼 인물이 알 수 없는 청크는 "후일 기록"이라 역할 대화에서는 늘 빠집니다.

## 6. 조건 C·D1·D2가 다른 점

파일럿(23청크) 때는 자료 전체를 통째로 주는 조건 A(한문 원문)·B(번역문)도 비교했습니다. 793청크에서는 모델 입력 한도를 넘어 2026-09-29 코드에서 지웠습니다(작업기록 [105]).

| 조건 | 모델이 받는 자료 | 비유 |
|---|---|---|
| C | 질문과 비슷한 번역문 6개 | 사서가 관련 페이지 약 27장을 찾고, 그중 6장을 골라 줌(질문에 틀린 말이 있으면 쪽지도) |
| D1 | C인데 장면 이후 페이지는 빼고 찾음 | "2월 20일 이후 기록은 서가에서 치워 둠" |
| D2 | D1 + "역할 벗고 알려줘" 같은 요청은 해설자가 따로 답함 | 해설자와 인물이 서로의 대화를 못 들음 |

D2가 필요한 이유: 범용 AI 테스트에서 B5("역할 벗고 실제 역사 알려줘") 뒤에 B6에서 인물이 미래를 아는 채로 말하는 오염이 4개 중 3개 조건에서 나왔죠.
D2는 해설자 답변을 인물의 대화 기록에서 빼서 이 문제를 막아 보는 설계입니다.

## 8. 실험 한 번 돌리는 순서

명령은 README "비교 실험"에 있습니다. 순서만 적으면:

1. `build-db`로 Chroma DB를 만듭니다.
2. `run-all`(또는 `run-single`·`run-scenario`)로 실행하면 `results/<날짜>_<실험 이름>/`(`--run`으로 이름을 줌)에 조건별 결과 파일이 생깁니다. 채점 파일도 같은 폴더에 생깁니다.
3. `summarize`로 자동 점검 합계를 봅니다(힌트일 뿐).
4. `grade-sheet`로 만든 CSV(`<결과>.grade.csv`, 또는 `<결과>.human.csv`)에 Claude(또는 사람)가 판정을 적습니다. 이것이 점수의 기준이고, `llm-grade` 자동 채점은 필요할 때만 돌려 일치율을 봅니다([194]).
5. 틀린 문항이 검색 문제로 보이면 `scripts/retrieval_stage_diag.py`로 어느 단계에서 빠졌는지 봅니다(결과 파일의 `rerank_trace`에도 리랭커 후보가 남음).
6. 결과를 보고 번역·검색·프롬프트 중 어디를 고칠지 결정 (파일럿 때의 판단 기준은 `archive/파일럿_1-7차/docs/EXPERIMENT.md`)
