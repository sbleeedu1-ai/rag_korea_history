# 구조 비교: 실록 RAG vs 법령 챗봇 2개

비교 대상
- **강사 레포** `woooyoung/Lease_Protection_Act` (임대차 법령 챗봇, 파이썬 파일 7개·약 460줄)
- **내 레포** `sbleeedu1-ai/rag-law-chatbot_challenge` (법률 RAG 챗봇, 실행 파일 4개·약 940줄 + back_up/)
- **실록 RAG** `rag_korea_history_test` 브랜치 `claude/project-thread-df18ai` (패키지 9개 모듈 + 앱 + 테스트)

## 1. 뼈대는 셋 다 같아요

```
원문 → 정제 → 청킹 → 임베딩 → Chroma(로컬) → 질문과 비슷한 청크 검색 → gpt-4o-mini 답변 → Streamlit 화면
```

"자료에 없으면 확인되지 않는다고 답하라", "근거 조항(기사 ID)을 붙여라", temperature 0, 청크마다 메타데이터를 달아 Chroma `where`로 거르기까지 같은 방식입니다.
실록 RAG가 완전히 새로운 구조가 아니라, 알고 계신 구조에 **이 프로젝트에만 필요한 단계 몇 개를 더 붙인 것**이라고 보시면 됩니다.

## 2. 한눈에 비교

| 항목 | 강사 레포 | 내 법령 레포 | 실록 RAG | 왜 이렇게 했나 |
|---|---|---|---|---|
| 원문 | 한국어 법령 PDF | 한국어 법령 PDF | **한문** XML | 한문은 그대로 검색·답변이 어려움 |

| 청킹 기준 | 조/항 | 조/항/호 | 문단 + **화자 전환**(上曰, 萬理等對曰, 翌日) | 한 문단에 세종·최만리·다음 날 사건이 섞여 있음 |

| 코드 모양 | 스크립트 몇 개 (가장 단순) | 큰 파일 4개 + back_up/ 버전들 | 작은 모듈 여러 개 + 명령어(cli) + 테스트 | 조건 5개를 같은 코드로 돌려야 해서 부품을 나눔 |

## 3. 실록 RAG가 더 나은 점 (이 프로젝트 기준)

1. **시점 필터**: 법령은 "어느 법이냐"만 거르면 되지만, 역사 인터뷰는 "언제까지 아는가"를 걸러야 합니다. 기사 날짜와 실제 사건 시점을 따로 저장해서, 2월 20일 기사 안의 다음 날 석방 문장도 걸러집니다.
2. **번역을 파일로 분리**: 번역이 틀린 곳을 `corpus.jsonl`에서 고치고 다시 build만 하면 됩니다. 오답노트 → 수정 → 재측정 흐름이 쉬워요.
3. **실험을 같은 코드로 반복**: A~D2 다섯 조건을 한 명령(`run-all`)으로 같은 질문에 돌리고 결과 파일로 남깁니다. "개선 전/후 수치"를 만들기 쉽습니다.
4. **테스트**: 번역 청크가 원문을 빠짐없이 덮는지, 시점 필터·해설자 분리가 제대로 동작하는지 자동으로 확인합니다. 두 레포의 `back_up/` 같은 버전 파일 대신 git 기록으로 관리해요.

## 4. 두 레포가 더 나은 점 (가져올 것)

1. **청킹 전략 비교 (A vs B)**: 둘 다 있고 과정 요구사항입니다. 실록 RAG에도 "고정 길이 + 겹침" 컬렉션을 추가해야 해요.
2. **후속 질문 바꿔쓰기**: "그럼 정창손은?"처럼 짧게 물으면 지금 검색은 약합니다. 강사 레포처럼 검색 전에 독립 질문으로 바꾸는 단계를 넣으면 좋아요.
3. **`.env` 사용**: 키 관리 방식을 강사 레포와 같게 맞추는 게 설명하기도 쉽습니다.
4. **단순함**: 강사 레포는 파일 하나가 한 가지 일만 해서 읽기 쉽습니다. 실록 RAG는 실험 기능 때문에 파일이 많은 편이라, 구조 설명 문서로 보완했어요.
5. **로컬 임베딩(bge-m3)**: 과정에서 같은 모델을 쓰면 비교가 쉽고 API 비용이 없습니다. 원하시면 선택지로 추가할 수 있어요.
